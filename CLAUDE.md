# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Django REST API for a gamecock (fighting-cock) breeding management system (ระบบจัดการการฝากผสมไก่ชน). Admins manage breeder (stud) master data and approve bookings/payments; customers register their hens and book breeding slots with a breeder, paying a deposit that an admin must verify before the booking locks a queue slot.

The authoritative schema/architecture reference is `docs/design/step1-system-analysis-database-design.md` (STEP1 design doc) — read it for the full 15-entity ER diagram, FK matrix, constraint matrix, and state machines before making schema changes. Note: it's the *original* design: the ER/FK/constraint structure is still accurate, but some literal field names and status enums (Booking, Payment) were renamed in a later step — see "Booking/Payment field names" below, and always trust the model file over the doc for current field names.

## Commands

Windows venv — use `venv/Scripts/python.exe`, not `venv/bin/`.

```bash
# install deps
venv/Scripts/python.exe -m pip install -r requirements.txt

# env setup (once) — copy and fill in real values; never commit the real .env
cp .env.example .env

# migrations
venv/Scripts/python.exe manage.py makemigrations <app>   # verify with --check --dry-run before committing
venv/Scripts/python.exe manage.py migrate

# dev server
venv/Scripts/python.exe manage.py runserver

# tests (pytest-django, configured via pytest.ini)
venv/Scripts/python.exe -m pytest apps                                   # whole suite
venv/Scripts/python.exe -m pytest apps/bookings                          # one app
venv/Scripts/python.exe -m pytest apps/bookings/tests.py::BookingCRUDTests::test_customer_can_create_booking  # one test
```

- The test suite requires a real PostgreSQL connection (no sqlite fallback — `config/settings.py` hard-codes the postgresql backend and reads `DB_*` from the environment with no defaults). Never run two `pytest` invocations concurrently — they race on creating/tearing down the same Postgres test database and produce spurious failures.
- The full suite takes several minutes; race-condition tests (`ConcurrentBookingTests` in `apps/bookings/tests.py`) use `TransactionTestCase` with real Python threads and `select_for_update()` against Postgres to prove locking actually serializes concurrent requests — they need real DB row locks, so they're meaningless (or hang) against sqlite.
- When a migration renames or removes a field that already shipped, `makemigrations` will try to interactively ask "did you rename X to Y?" — this hangs in a non-interactive shell. Prior steps handled this by hand-writing the migration's `RenameField`/`AddField`/`RemoveConstraint`+`AddConstraint` operations directly, then confirming with `makemigrations --check --dry-run` that the result exactly matches the model state before applying.
- Django admin at `/admin/`; API docs at `/api/v1/docs/` (Swagger), `/api/v1/redoc/`, `/api/v1/schema/` (drf-spectacular).

## Architecture

**Build state**: `accounts`, `core`, `breeders`, `hens`, `bookings`, `payments`, `breeding`, `hatching`, `chicks`, `health`, `vaccinations`, `documents` are fully implemented (models + serializers + services + views + permissions + urls + tests). `notifications`, `reports` currently only have models/admin/migrations scaffolded from the design doc — their `views.py`/`tests.py` are still Django's default placeholder, no API layer yet.

**Layering is deliberate and consistent across every implemented app** — follow it for anything new:
- `views.py` stays thin: permission wiring + calling a serializer + calling a service function. No business logic in views.
- `services.py` owns all business logic and every DB mutation of consequence. Any operation that changes money, queue slots, or running numbers wraps in `transaction.atomic()` and takes `select_for_update()` on the contended row(s) — see `apps/core/services.next_running_number` and `apps/bookings/services.lock_booking_slot`/`approve_booking` for the pattern (lock → re-check invariant → mutate). Business-rule violations are raised as `apps.core.exceptions.AppError(code, message, http_status=...)`, never returned ad hoc from a view.
- `serializers.py` owns input validation and read/write field shaping. Fields that must never come from the client (price, owner/customer id, role, created_by, status, running numbers) are `read_only` on the serializer and set inside the service layer from `request.user` / server-computed values instead.
- `permissions.py` holds custom DRF permission classes per app; `apps.core.permissions.IsOwnerOrAdmin` is the shared object-level IDOR guard (any model exposed to customers implements `get_owner_user_id()` — see the Data Ownership Matrix §12 in the design doc for the full ownership chain across all 15 entities), and `apps.core.permissions.IsAdminRole` gates admin-only actions/fields.

**Cross-cutting conventions**:
- Standard error envelope for every API error — `{"error": {"code": "...", "message": "...", "details": {...}}}` — produced by `apps.core.exceptions.standard_exception_handler`, wired as DRF's global `EXCEPTION_HANDLER`.
- Sequential business numbers (wing clip numbers, booking numbers, payment numbers, document numbers) all go through the single `apps.core.models.RunningNumberCounter` + `apps.core.services.next_running_number()` mechanism (row-locked per `(counter_type, year)`) — never invent a separate sequence generator.
- File/image uploads (`Breeder.image`, `Hen.image`, `Payment.slip`) all use `apps.core.validators.validate_image_file` via the model field's `validators=[...]` — Pillow-backed: extension + content-type whitelist, 5MB cap, decodes the file to confirm it's genuine image data. DRF's ModelSerializer picks this up automatically from the model field, so new image fields just need the same validator attached.
- API is versioned under `/api/v1/` (`config/urls.py`); each app owns a `urls.py` with a DRF `DefaultRouter`, included from the central `api_v1_patterns` list there.
- Auth is JWT (`rest_framework_simplejwt`, rotation + blacklist-after-rotation). Exactly two roles, no separate Role/Permission tables — `apps.accounts.models.User.role` is `ADMIN` or `CUSTOMER`. Ownership/role is always read from `request.user` in the service layer, never trusted from client-supplied ids — this is enforced project-wide (see e.g. `Hen.owner`, `Booking.customer`, `Breeder.created_by`).

## Booking/payment domain notes

- Booking status machine (`apps/bookings/models.py Booking.Status`): `PENDING → WAITING_PAYMENT → PAID → APPROVED → IN_PROGRESS → COMPLETED`, with `CANCELLED`/`REJECTED` reachable from any non-terminal state. This is a later-step revision of the design doc's §9.1 (7-value) state machine.
- Field renames since the design doc: `Booking.agreed_price/amount_paid/balance_due` → `price/paid_amount/remaining_amount`; `Payment.slip_image_path/reviewed_by/reviewed_at/reject_reason` → `slip/verified_by/verified_at/remark`. The doc's ER/FK/constraint structure otherwise still applies.
- A breeder's monthly queue capacity (`Breeder.default_monthly_quota`, `BreederMonthlyQuota`) is only consumed when a booking is admin-approved (`apps.bookings.services.approve_booking` → `lock_booking_slot`), not at booking creation — creation only enforces "one active booking per hen" via a DB partial unique index (`uq_booking_hen_active`), backed up by catching the resulting `IntegrityError` for the race case.
- `price`/`deposit_amount` are always server-computed snapshots from `Breeder.service_rate` at booking-creation time (`apps.bookings.services.calculate_booking_amount`, deposit = 30% — a documented assumption, not a spec'd number) — never accepted from the client.

## Breeding process / egg tracking domain notes (STEP6)

- `apps.breeding.models.BreedingEvent` is an append-only event log per Booking (`/api/v1/breeding-events/`). Flow: `RECEIVED → BREEDING → BREEDING_COMPLETED → WAITING_EGG → EGG_LAID → INCUBATION → HATCHING`. This **replaces** the STEP1 §4.7/§9.3 5-stage `BreedingTimeline`/`Stage` design (renamed via a hand-written migration, `apps/breeding/migrations/0002_breeding_step6_fields.py`) — `stage`→`status`, `note`→`description`. `Booking.current_breeding_stage`/`Booking.BreedingStage` (the old 5-value cached field on Booking itself) is untouched/legacy and intentionally not wired to this new flow — treat it as dead weight, not a second source of truth.
- Allowed transitions are centralized in `apps.breeding.services.BREEDING_TRANSITIONS` (a `{current_status: next_status}` map, `None` = no event yet, `HATCHING` = terminal) and enforced by `transition_breeding_status()`; skipping or reversing a stage raises `AppError('INVALID_BREEDING_TRANSITION')`. Only ADMIN can write; a booking must be `APPROVED`/`IN_PROGRESS` (never `PENDING`/`WAITING_PAYMENT`/`PAID`/`CANCELLED`/`REJECTED`) for an event to be recorded.
- Duplicate-event protection is layered exactly like queue/payment races elsewhere: a DB `UniqueConstraint` on `(booking, status)` is the authoritative guard; `record_breeding_event()` takes `select_for_update()` on the Booking row first, which in practice fully serializes concurrent submissions for the same booking (the loser observes the winner's already-committed event and fails on the transition check, not a raw `IntegrityError`) — but the constraint + `IntegrityError` catch stay in place as defense-in-depth for any caller that bypasses the lock (e.g. direct `BreedingEvent.objects.create()`, Django admin).
- `apps.breeding.models.Egg` (`/api/v1/eggs/`) tracks one row per egg-laying batch per booking: `total_eggs`/`good_eggs`/`bad_eggs` (DB `CheckConstraint`s enforce all `>= 0` and `good_eggs + bad_eggs <= total_eggs`), `egg_date`/`incubation_date`. This **replaces** the STEP1 §4.8 `lay_date`/`egg_count`/`note` fields (same migration as above) — `apps.hatching.models.Hatching.egg` FK is untouched, only the doc comment referencing `Egg.egg_count` was updated to `Egg.total_eggs`. `apps.breeding.services.calculate_good_egg_rate()` returns `good_eggs / total_eggs * 100` (2 dp, `0.00` when `total_eggs == 0`), exposed read-only as `good_egg_rate` on `EggSerializer`.
- Both `BreedingEventViewSet` and `EggViewSet` only expose create/list/retrieve — no update/delete — per the explicit rule that a customer must never edit the timeline; corrections are new events, not edits. `apps.breeding.permissions.BreedingWritePermission` is ADMIN-write/anyone-authenticated-read, combined with per-object `get_owner_user_id()` ownership scoping (both in `get_queryset()` and `has_object_permission()`, same double-layer IDOR pattern as `BookingActionPermission`).
- Both create serializers use `PrimaryKeyRelatedField(queryset=Booking.objects.all())` for `booking` (same pattern as `BookingCreateSerializer`/`PaymentCreateSerializer`), so a nonexistent booking id is rejected at the serializer layer (400) before the service runs — the service's own `AppError('NOT_FOUND', ...)` check is reachable only by callers that bypass the serializer.

## Hatching / Chick / Health / Vaccination domain notes (STEP7)

- `apps.hatching.models.Hatching` (`/api/v1/hatchings/`) is a two-phase lifecycle against one `Egg` batch: `apps.hatching.services.start_hatching()` creates the row (`status=INCUBATING`, `total_eggs` snapshotted server-side from `egg.total_eggs`, `completed_at` null) via `POST /api/v1/hatchings/`; `apps.hatching.services.complete_hatching()` later fills in `completed_at`/`hatched_count`/`failed_count`/`survival_count` and flips `status` to `HATCHED` (if `hatched_count > 0`) or `FAILED`, via `PATCH /api/v1/hatchings/{id}/complete/`. This **replaces** the STEP1 §4.9 `hatch_start_date`/`hatch_end_date`/`note` fields (hand-written migration `apps/hatching/migrations/0002_hatching_step7_fields.py`) — `hatch_start_date`→`started_at`, `hatch_end_date`→`completed_at`, `note`→`remark`; `hatched_count` itself is unrenamed. DB `CheckConstraint`s enforce all counts `>= 0`, `hatched_count + failed_count <= total_eggs`, `survival_count <= hatched_count`, and `completed_at >= started_at` (or null). `apps.hatching.services.calculate_hatching_rate()` returns `hatched_count / total_eggs * 100` (2 dp, `0.00` when `total_eggs == 0`), exposed read-only as `hatching_rate` on `HatchingSerializer` — same "computed, not stored" convention as `Egg.good_egg_rate` (STEP6).
- `apps.chicks.models.Chick` (`/api/v1/chicks/`) gained `booking` (denormalized FK, always set server-side from `hatching.egg.booking`, **never used for ownership** — see below), `name`, and `hatch_date`→`birth_date` (hand-written migration `apps/chicks/migrations/0002_chick_step7_fields.py`). `wing_clip_number` generation (`apps.core.services.next_running_number`/`format_wing_clip_number`, STEP1-era) is untouched — a dedicated wing-clip management API is explicitly STEP8 scope per the spec, so this step only kept the existing auto-generation working, not built new surface around it. `apps.chicks.services.create_chick()` now takes `hatching_id` (not a `Hatching` instance) and enforces, in addition to the pre-existing "batch must be HATCHED" rule: the number of `Chick` rows for one `Hatching` must never exceed its `hatched_count` (`select_for_update()` on the `Hatching` row serializes concurrent calls so this count check can't race), and `birth_date` must be within `[hatching.started_at, today]`.
- **Ownership chain is deliberately not shortcut-able**: `Chick.get_owner_user_id()` still walks `self.hatching.egg.booking.customer_id` (the real `User → Booking → Hatching → Chick` chain), *not* the denormalized `booking` field — `HealthRecord`/`Vaccination` delegate to `chick.get_owner_user_id()` in turn. The `booking` FK on `Chick` exists only for cheap filtering/reporting; never use it (or any client-supplied `chick_id` alone) as an authorization shortcut.
- `apps.health.models.HealthRecord` (`/api/v1/health-records/`): `weight_grams`→`weight`, `health_status`→`observation` (widened `CharField(50)`→`TextField`), `treatment_note`→`remark`, plus a new `medicine` field (hand-written migration `apps/health/migrations/0002_health_step7_fields.py`). `apps.health.services.record_health()` rejects `weight < 0` and `record_date` outside `[chick.birth_date, today]`.
- `apps.vaccinations.models.Vaccination` (`/api/v1/vaccinations/`): `vaccine_date`→`vaccination_date`, `administered_by`→`recorded_by`, `note`→`remark`, `dose` (free text) replaced by `dose_number` (int, `>= 1`), `next_due_date` removed, and a new `age_days` field — always computed server-side in `apps.vaccinations.services.record_vaccination()` as `(vaccination_date - chick.birth_date).days`, same "computed snapshot, never client-supplied" convention as `Booking.price`/`Vaccination.age_days` is nullable at the DB level only because raw `.objects.create()` bypassing the service can't compute it (hand-written migration `apps/vaccinations/migrations/0002_vaccination_step7_fields.py`). Duplicate doses are rejected twice over: DB `UniqueConstraint` on `(chick, vaccine_name, dose_number)`, which DRF also surfaces as an automatic `UniqueTogetherValidator` (400) on `VaccinationCreateSerializer` since all three fields are present on it — same free protection STEP6 noted for `BreedingEvent`.
- All four new viewsets (`HatchingViewSet`, `ChickViewSet`, `HealthRecordViewSet`, `VaccinationViewSet`) follow the STEP6 `BreedingEventViewSet` shape exactly: ADMIN-write/owner-read permission class per app (`HatchingWritePermission` etc., all structurally identical to `BreedingWritePermission`), create/list/retrieve only (no update/delete), `PrimaryKeyRelatedField` for the parent FK on the create serializer (so a missing parent is a 400 at the serializer layer, with the service's own `AppError('NOT_FOUND', ...)` as defense-in-depth for callers that bypass it).

## Document generation / PDF / pedigree domain notes (STEP8)

- `apps.documents.models.Document` (`/api/v1/documents/`) gained `document_no`→`document_number` (matches the `booking_number`/`payment_number` naming convention — was inconsistent before), `DELIVERY_HISTORY`→`DELIVERY_DOCUMENT`, `file_path` widened from a plain `CharField` to a real `FileField` (`upload_to=document_upload_path`, saved via `.file_path.save(name, ContentFile(pdf_bytes))` — same "server-generates-and-saves" idiom as an upload, just without a client-supplied file), and a new `UniqueConstraint(fields=['chick', 'document_type'], condition=Q(chick__isnull=False))` (hand-written migration `apps/documents/migrations/0002_document_step8_fields.py`; `apps/core/migrations/0003_runningnumbercounter_delivery_no.py` adds the matching `DELIVERY_NO` counter type). `CONTRACT` (booking-based) is untouched scaffold — only the two chick-based types (`PEDIGREE_CERTIFICATE`, `DELIVERY_DOCUMENT`) get a generation/PDF flow in this step; the `DocumentGenerateSerializer`'s `document_type` `ChoiceField` deliberately excludes `CONTRACT` so it can't be requested through this endpoint at all (422 `INVALID_DOCUMENT_TYPE` is the service-layer backstop for callers that bypass the serializer).
- `apps.documents.services.generate_document()` is the STEP6/7-style lock → re-check → mutate pattern applied to file generation: `select_for_update()` on the `Chick` row serializes concurrent requests for the same `(chick, document_type)`, a plain pre-check (`Document.objects.filter(...).exists()`) rejects the ordinary duplicate case cheaply (`409 DUPLICATE_DOCUMENT`) *before* a running number is spent or a PDF is rendered, and the DB `UniqueConstraint` + `IntegrityError` catch is the race backstop — in practice the row lock fully serializes same-chick requests (like `BreedingEvent` in STEP6), so the loser almost always hits the cheap pre-check, not the `IntegrityError` path. The whole function is one `transaction.atomic()`; if `render_document_pdf()` raises, the entire transaction (including the already-incremented `RunningNumberCounter`) rolls back, so a failed generation never leaves an orphaned `Document` row or wastes a document number — verified directly in `test_pdf_generate_error_wrapped_and_no_row_left_behind`.
- `apps.documents.pdf.render_document_pdf(document, chick)` is the only place PDF content is decided, and it reads every value straight off `chick`'s relationship chain (`chick.hatching.egg.booking.{customer,breeder,hen}`, `booking.breeding_events`, `chick.health_records`, `chick.vaccinations`) — the create endpoint accepts only `chick` + `document_type`, never body content, so a client cannot dictate what appears on a generated certificate. Uses `reportlab.platypus` (not the low-level `Canvas`) specifically so history sections (breeding events, health records, vaccinations) auto-paginate instead of needing manual y-position/page-break tracking.
- **Thai font gotcha**: ReportLab's built-in fonts (Helvetica/Times) have no Thai glyphs — Thai characters silently render as filled boxes with no warning, and worse, extract back out as `■` (unreadable) rather than raising an error, so this can go unnoticed without an explicit content-accuracy test. `apps.documents.pdf._thai_font_name()` looks for a Thai-capable TTF at runtime (project-local `apps/documents/fonts/Thai.ttf` first, then the open-source TLWG fonts Debian/Ubuntu installs via `apt install fonts-thai-tlwg`, then the fonts Windows/macOS ship with) and registers whichever it finds first; **this repo does not bundle a font file** (Tahoma etc. are not freely redistributable) — a from-scratch Linux deployment with no Thai font installed will silently fall back to Helvetica and produce boxes instead of Thai text. Whoever provisions the production host must install a Thai-capable font (`apt install fonts-thai-tlwg` is the easiest fix on Debian/Ubuntu) or drop a properly-licensed one at `apps/documents/fonts/Thai.ttf`.
- `apps.documents.views.DocumentViewSet.download` (`GET /api/v1/documents/{id}/download/`) streams the saved PDF via `FileResponse`; `apps.documents.services.get_document_file()` raises `AppError('FILE_MISSING', ..., 404)` if the row has no file or the underlying storage object is gone (simulated in tests via `document.file_path.delete(save=True)`) rather than letting a missing-file `IOError` surface as a raw 500.
- Ownership for `Document` spans two different chains depending on type (`booking.customer_id` for `CONTRACT`, `chick.get_owner_user_id()` — i.e. the full `User → Booking → Hatching → Chick` chain — for the two STEP8 types), so `DocumentViewSet.get_queryset()` filters with `Q(booking__customer=user) | Q(chick__hatching__egg__booking__customer=user)` rather than a single FK lookup like every other STEP6/7 viewset.
